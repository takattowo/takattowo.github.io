Building DevTools for Claude Code, with Claude Code

2026-05-15

There's a moment, when you've been pair-programming with an AI for a few weeks, where it stops feeling like a parlor trick and starts feeling like... something else. Not magic. Not a colleague. Something in between. A weirdly competent ghost that lives inside your terminal, scrolls past your screen at superhuman speed, and occasionally, very politely, deletes the wrong file.

That ghost is Claude Code. I've been using it as my daily driver for a few months now, and the thing that kept bothering me wasn't that it made mistakes (it does, but so do I), and it wasn't that it was slow (it isn't, mostly). It was that I couldn't see what it was doing.

Sure, the terminal scrolls. Tool calls flash by. A spinner spins. A long edit lands and something works or doesn't. But after a session ends, I had no real way to answer the questions I actually cared about:

  • Where did all my tokens go?
  • Which files did this thing thrash on the most?
  • Why did that one task cost me $1.40 when the next one cost twelve cents?
  • Did it read the same file six times or am I imagining things?

I wanted Chrome DevTools, but for my AI. A timeline. A heatmap. A scrubber. Something I could leave open in a second monitor and just watch.

So I built it. With the AI. Watching itself.

This is the story of that, including the parts where things went sideways.

The seed: "wait, where does this stuff actually live?"

The first useful realization was a boring one. Claude Code already writes everything it does to disk. Every session, every turn, every tool call, every byte of every file read, every token of every response. It all lands in a JSONL file under ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl.

So I didn't need to hook into the model. I didn't need any kind of clever instrumentation. I just needed to tail those files and turn the raw events into something a human could squint at.

That changed everything. The problem went from "build an observability platform for an LLM" to "build a glorified log viewer". And glorified log viewers are deeply within my powers.

I opened a fresh repo, called it cli-talker (the package name stuck even after I renamed the project to claude-code-devtools for clarity), and asked Claude Code to help me scaffold a pnpm monorepo.

It did. Five packages, roughly:

  • core: types, the database layer, the normalizer that turns raw events into a unified schema.
  • adapter-claude-code: the bit that knows how to parse Claude Code's specific JSONL format.
  • server: Fastify HTTP + WebSocket, file watcher, REST routes.
  • web: React SPA with the timeline and heatmap.
  • The CLI binary itself, just a thin wrapper that boots the server and opens your browser.

That separation between core and adapter-* mattered a lot more than it sounds. The whole point was that one day I'd want to plug in Codex, or Cursor, or Gemini CLI, and treat them all as instances of the same abstraction. An AgentAdapter knows how to discover sessions and readChunk events. Everything downstream (storage, normalization, the UI) never has to care which agent it came from.

This is the kind of architectural decision that, if I were building alone, I might have skipped on day one and regretted on day forty. Pair-programming with Claude, it came almost for free. I described the shape I wanted, it pushed back on a couple of things (rightly), and we landed on something I still haven't had to rewrite.

The first build

The first version was, honestly, kind of magical to use.

node packages/cli/dist/index.js

Browser opens. Empty timeline. I open a second terminal, start a Claude Code session, ask it to do something (anything), and within about a second and a half, rows start streaming into my browser.

Read. Read. Edit. Bash. Read. Edit. WebFetch. Edit.

Each row colored by tool, each one stamped with a duration and a file path, all of it ticking past in real time. Watching the agent work felt like watching a long-exposure photograph develop. Suddenly I could see the shape of a session. The thinking parts (lots of small reads, quick edits) versus the slogging parts (one Bash call that takes twenty seconds, then nothing, then a wall of text).

The file heatmap landed next, and that's when I started noticing things I didn't want to notice. Like the time Claude read the same package.json four times in a single task. Or the time it edited a file, re-read it, edited it again, re-read it again. Each one a small sin, individually defensible. Collectively: a couple thousand tokens I didn't need to spend.

This is the recurring lesson of building DevTools for any system: you'll find embarrassing things and then you'll have to decide what to do about them.

The bug that broke my brain: "model: unknown"

I want to tell you about this one because it captures what working with an LLM on a real project actually feels like.

I shipped the dashboard view. Top tools, top files, cost by model, total tokens spent across all sessions. The whole bird's-eye view. I opened it up, looked at my last week of activity, and saw something deeply weird:

Model: unknown. Cost: $0.00.

For every single session.

This was not what I wanted my dashboard to say. My dashboard had one job. Its job was to tell me how much money I'd spent. And it had decided the answer was zero. This was, in a strict accounting sense, incorrect.

I asked Claude to help me debug. We started where you start: the normalizer. The piece that takes raw events and turns them into the schema the rest of the app uses. Surely the issue was there. Surely we were dropping the model field somewhere in the pipeline.

It wasn't dropping it. The model field was making it into the database fine, for some sessions. For others, the very first event in the JSONL didn't include a model name at all. It only appeared a few turns in, after the first assistant response.

This is where it got interesting. The normalizer was using an INSERT ON CONFLICT pattern to upsert sessions as new events streamed in. To prevent later events from overwriting earlier metadata, certain fields (including model) were marked as immutable after first write.

You can see the trap. The very first event didn't have a model. So the session got persisted with model: null. The second event had the model. But by then, the field was immutable. The session was stuck with "unknown" forever.

Once we found it, the fix was small. Change the upsert logic to allow the model field to be filled in if and only if it was previously null. Re-run against the full session corpus. Watch the dashboard light up with proper model names and proper costs.

But the journey to that fix was, I think, the most quintessentially "AI pair-programming" experience I've ever had. Claude was relentless. It wrote tests, it traced the code path, it offered three plausible hypotheses, it ruled out two of them, and then (and this is the part that still surprises me), it caught its own earlier reasoning mistake and corrected itself without me having to prompt it.

It's not that I couldn't have found the bug alone. I would have, eventually. It's that the speed of the loop was different. The "what if it's this", "let me check", "no, it's not that" cycle, which usually takes me an hour with coffee breaks, took fifteen minutes.

I deleted the old SQLite store, restarted the server, watched the dashboard rebuild itself with 184 sessions across half a dozen models. Zero unknowns. Real numbers. A real total cost. (Which, I should admit, was higher than I expected. The dashboard immediately started doing its actual job, which was making me uncomfortable.)

The CI fight

Every project has a moment where the actual code is done and you spend two days fighting with CI.

For this one, it was the moment I decided to publish to npm. The whole pitch of the project was "you should be able to type npx claude-code-devtools and have it just work." That means bundling. That means a build step that produces a single, self-contained JavaScript file the user can run without installing a monorepo's worth of dependencies.

The first attempt failed because the bundled CLI assets were being picked up by ESLint and flagged. Of course they were. The bundled file is, by definition, ugly machine-generated JavaScript, and our lint config (sensibly) didn't want anything to do with it.

Fix: exclude the bundled output from ESLint.

The second attempt failed because typecheck was running before build, and the typecheck stage was trying to validate generated types that didn't exist yet.

Fix: reorder the CI steps so build runs first.

The third attempt failed because of OIDC token configuration on the npm publish action. This one I'll spare you. It involved a lot of staring at GitHub Actions logs and reading documentation about scoped tokens. It got fixed.

By the fourth attempt, npx claude-code-devtools worked. Anyone could install it. The README badges all turned green. The release pipeline was real.

There's a particular kind of satisfaction in that moment. The project went from "thing I'm building" to "thing that exists". A small ceremony. A green checkmark. A version number that means something to npm's registry.

--redact, or: the demo problem

I wanted to record a demo. A short GIF of the timeline scrolling, the heatmap filling in, the inspector showing token counts. Pure marketing material.

I opened my own dashboard, hit record... and immediately panicked. Because the timeline was full of file paths. And the inspector was showing actual prompt content. And, oh god, somewhere in there was probably an API key that I had cat'd during some earlier debugging session.

This was a design flaw, and not a small one. The whole appeal of a local DevTools is that you can see everything. The whole horror of recording a demo is that you can see everything.

The solution was --redact. A CLI flag that takes a list of regex patterns and strips matches from the timeline before they reach the browser. Critically (and this part I'm proud of), the redaction happens at the API layer, not at storage time. The underlying SQLite database is untouched. You can turn redaction off and your original data is right there.

We seeded a default list of patterns: Anthropic keys, GitHub tokens, AWS access keys, Google API keys, Slack tokens. The usual suspects. Users can add their own with --redact "MY_PATTERN". It's not perfect (no regex-based redaction ever is), but it lets me hit record without my heart rate spiking.

This was the first feature I built thinking about other people using the tool, rather than just me. And it changed the way I thought about every subsequent feature. Once you've designed for paranoid users, you can't un-design.

The plugin

The next leap was making claude-code-devtools itself a Claude Code plugin.

This is where the recursion gets fun. Claude Code plugins are little bundles of slash commands, skills, and hooks that extend the agent's behavior. If I packaged my DevTools as a plugin, I could ship a /devtools slash command that booted the server with one keystroke, and (more interestingly) I could register hooks that captured additional events the JSONL wouldn't normally surface.

SessionStart. PostToolUse. UserPromptSubmit. Stop. Each one a chance for the plugin to POST a small JSON blob to my running server (POST /api/ingest/hook) and enrich the timeline with information that wasn't in the transcript file at all.

This is the part where I had to stop and laugh, because the symmetry was getting absurd. I was using Claude Code to build a plugin for Claude Code that captured events from Claude Code so I could watch Claude Code work better. Strange loops all the way down. At some point in the process, I asked Claude to help me write the documentation for the plugin, and the plugin documented its own purpose, in a file that was being live-streamed into the dashboard I was looking at.

I am not sure this is what people meant when they talked about "AI alignment" but I am pretty sure it is funny.

The plugin shipped as v0.1.4. Install it from the marketplace, type /devtools, server starts, browser opens, hooks register, you're in. Total ceremony: about three seconds.

The 7d/30d bug

You ship a release. You feel good. You take a screenshot of the dashboard for a tweet. You click the "7 days" filter to scope the screenshot to recent activity.

The dashboard goes empty.

You click "30 days". Still empty. You click "all time". Everything's back.

This was v0.1.4's parting gift to me. The dashboard date preset filtering was broken in a really specific way: the preset range was being computed at component-render time using Date.now(), but the resulting object was being used as a React Query key. Because the timestamp moved every millisecond, the query key was unstable, the cache was constantly invalidating, and the API was being called with subtly wrong parameters.

The fix was to move the preset range computation inside the queryFn, so the cache key stayed stable. Same pattern broken in two places (dashboard and sessions sidebar), same fix.

Shipped as v0.1.5. Five-minute fix, hour-long diagnosis. The classic ratio.

This is the kind of bug that's genuinely interesting to debug with an AI partner, because the symptom (empty dashboard) is several layers removed from the cause (unstable timestamps in query keys), and the path between them goes through React, TanStack Query, your network tab, and your API layer. Tracing that chain alone is annoying. Tracing it with someone who can read all the relevant files in parallel is a different experience entirely.

The tiny one

I'll end with the one that's barely worth mentioning, except it's the one I'm most attached to.

When you switch between sessions in the sidebar, the main view used to reset to the timeline tab, even if you were looking at the heatmap. Every. Single. Time.

This was, technically, working as intended. The state reset on session switch. It was deliberate. It was three lines of code in a Zustand action.

It was also driving me insane, because I'd developed a workflow where I'd open the heatmap, click through sessions one by one, looking for the one with the most file thrash. Each click sent me back to the timeline. Each click I had to click "Heatmap" again.

I asked Claude to remove the reset. It removed the reset. It rebuilt. I tested it. The tab persists now. v0.1.6.

That was last week. I don't know if anyone else will ever notice this change. I notice it every single day, and every day, it makes me smile.

What I learned

If you're still here, here's the part where I try to extract a moral.

I think the thing that surprised me most about building with Claude wasn't that it was capable. I expected that, by now. What surprised me was how much it changed the shape of my decisions. With a fast pair-programmer, the cost of trying something is so low that the calculus around "should I refactor this?" or "should I add this feature?" inverts. The friction that used to push me toward "no, let's keep it simple" got replaced by "sure, let's see if it works".

This is dangerous in some ways. I shipped at least one feature I should have pushed back on. I scope-crept twice. I built things "because we could" rather than "because we needed to".

But it also unlocked stuff I would not have built alone. The pluggable adapter layer. The redact mode. The hook-based plugin. The dashboard with cost-by-model breakdowns. Each of these felt like a multi-day project on its own, and each one shipped in an afternoon.

The other thing I learned (and this one I think is durable) is that observability into your own workflow is wildly underrated. I built DevTools for Claude Code, and the very first useful thing it did was tell me I was using Claude Code badly. Not catastrophically. Just... wastefully. Reading files I'd already read. Asking it to summarize stuff that didn't need summarizing. Letting it thrash on edits that should have been one careful diff.

I'm now a slightly better operator of my own tools because I built a tool that watches me operate them. Recursive self-improvement. The cheap kind, where you just look at a graph and feel bad until you stop doing the thing the graph is mad about.

If you want to look at your own sessions, the install is one line:

npx claude-code-devtools

Or, if you're already inside Claude Code, the meta version:

/plugin marketplace add takattowo/claude-code-devtools
/plugin install claude-code-devtools@claude-code-devtools
/devtools

Open the browser tab. Start a session. Watch the rows scroll in.

It's a small thing. But it's the kind of small thing that, after a week of using it, you can't quite imagine going back to working without.

And that, I think, is the whole pitch.
